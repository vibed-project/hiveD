# hiveD

Read [docs/PROJECT.md](docs/PROJECT.md) first — it is the full design brief and the
source of truth for architecture questions this file doesn't answer. Read
[docs/adr/](docs/adr/) for decisions that go deeper than PROJECT.md on a
specific topic (identity/tokens, the vibeD executor contract, mindD usage).

## What this repo is

hiveD is a standalone control plane that defines, schedules, governs and
observes AI agents, running them in isolated sandboxes (vibeD by default)
and giving them durable memory (mindD by default). Vocabulary is normative —
use these words exactly, in code, docs, and UI, not synonyms:

| Term | Meaning |
|---|---|
| Hive | A hiveD installation (control plane instance). Multi-tenant. |
| Colony | Tenant / isolation boundary. |
| Agent | A versioned, immutable definition of an agent. |
| Run ("Worker" in prose) | One running instance of an Agent. |
| Cell | The isolated sandbox a Run executes in. |
| Session | Optional grouping of Runs sharing context and episodic memory. |
| Tool | A registered capability a Run may call. |
| Policy | Rules attached to a Colony or Agent. |
| Keeper | The control plane process. Binary `hived-keeper`. |
| Drone | The per-Cell runtime binary. Binary `hived-drone`. |

## Current milestone: M0 (foundations)

**In scope:** repo scaffold, ADR-0001–0004 (drafted), `proto/hived/v1alpha1`
for Colony/Agent/AgentVersion/Run/Event, a Postgres-backed resource store,
the Keeper's `apply/get/list/watch` API, the `hived` CLI skeleton
(`apply`/`get`/`watch`/`events` wired; `run`/`logs`/`approve` are stubs),
and a docker-compose dev loop.

**Out of scope — do not build these until told the milestone has moved:**
Scheduler / reconciliation controllers, the Executor interface and any
implementation (docker/vibeD/process), the `hived-drone` binary and its IPC
contract, the Model Gateway, the Tool Broker, real PASETO token issuance
(`internal/identity` is a no-op stub), real mindD integration or any mindD
Go client code, the Python SDK, the Helm chart, `examples/`, the Keeper's
MCP surface, and OpenAPI publication. If a task seems to require one of
these, stop and flag it rather than reaching past M0 — check with the user
before adding scope, and update this section when the milestone advances.

## Invariants

- Never make policy decisions in the Drone.
- Never execute agent logic in the Keeper.
- AgentVersion specs are immutable after creation; re-applying an identical
  spec is a no-op success, applying a *different* spec to an existing
  version is rejected.
- Events are append-only — no update, no delete.
- This module stays self-contained: no imports of sibling
  `github.com/vibed-project/*` modules or `memsidecar` (mindD). Enforced by
  `scripts/check-import-boundary.sh` in CI (`make boundary`). Cross-repo
  integration goes through an interface + generated client, never a direct
  module import.

## Build and test

**There is no host Go toolchain in this environment.** Every build/test
target runs inside a `golang:1.26` container via `scripts/go-in-podman.sh`.
Use `make build` / `make test` / `make lint` — do not suggest bare
`go build`/`go test` unless the user has confirmed they have a working host
toolchain. If you must run `go` directly, set `GOWORK=off` first (this repo
is deliberately not part of the sibling `go.work` at the workspace root —
see ADR-0004).

## Layout map

```
cmd/keeper/       hived-keeper binary: serve | migrate | version
cmd/hived/         hived CLI (Cobra)
internal/store/    Postgres resource store: apply/get/list/watch, migrations
internal/api/      Keeper API handlers (connect-go), one file per resource kind
internal/identity/ token issuance — stub only in M0
internal/config/   env-driven Keeper config
internal/obs/      slog + Prometheus + OTel wiring
internal/version/  ldflags-injected version info
proto/hived/v1alpha1/  resource + service definitions — source of truth
gen/               generated Go code from proto/ — never hand-edit
scripts/           check-import-boundary.sh, go-in-podman.sh
deploy/compose/    local dev docker-compose stack
```

## Codegen

`proto/` is the source of truth; `gen/` is generated by `make proto` (buf +
connect-go) and checked into git. Never hand-edit anything under `gen/`.
CI fails on drift (`buf generate && git diff --exit-code gen/`), so always
run `make proto` after touching a `.proto` file and commit the result.

## Conventions

- Logging: `slog`, structured fields, no `fmt.Println` in library code.
- Errors: wrap with `%w` and enough context to debug without a stack trace;
  don't swallow errors silently.
- Every behavior change comes with a test. Prefer table-driven tests.
- No third-party agent frameworks in the core (they're user code inside a
  Cell, not a hiveD dependency).
- Write in plain prose; no em dashes in docs or comments.
